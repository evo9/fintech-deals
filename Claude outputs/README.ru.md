# FDeals - прототип маркетплейса

Рабочий прототип маркетплейса M&A-сделок с финансовыми активами (лицензированные платёжные институты, EMI, крипто/VASP-компании, банки). Сделан как тестовое задание; продуктовый и визуальный ориентир - N5Deal.

В одном приложении три роли:

- **Покупатель** описывает, что ищет, просматривает и фильтрует активы, видит, насколько каждый актив совпадает с его интересами, и связывается с продавцами.
- **Продавец** публикует активы и управляет ими, просматривает и фильтрует покупателей (по желанию - с ранжированием относительно одного из своих активов) и связывается с покупателями.
- **Менеджер платформы** видит всех участников и все активы, подтверждает активы, блокирует или удаляет участников и активы, которые не соответствуют требованиям, всегда с указанием причины.

**Демо:** https://fintech-deals.vercel.app/

**Стек:** Next.js (App Router) · TypeScript strict · Prisma 6 · PostgreSQL (Supabase) · Tailwind + shadcn/ui · Vitest · Vercel

## Что посмотреть

1. **Покупатель с совпадениями** - войти как `lukas.weber@example.com`.
   - `/assets`: на карточках бейдж «Matches N of 5», зелёный «Strong match», когда совпали все заданные им критерии. Наведение или фокус на бейдже показывает, какие критерии совпали.
   - Включить **Only my interests**, переключить сортировку на **Best match**, поменять фильтры и перезагрузить страницу: состояние хранится в URL.
   - Открыть актив, нажать **Contact seller**; если диалог уже есть, вместо этого кнопка **Open conversation**.
   - `/profile`: изменить интересы, превью карточки справа обновляется сразу. Очистить все интересы и сохранить: профиль становится скрытым от продавцов, об этом сообщает подсказка.
2. **Продавец с диалогами** - войти как `seller.malta@example.com`.
   - `/buyers`: отфильтровать покупателей, в **Match buyers to your asset** выбрать один из своих активов, чтобы ранжировать покупателей по соответствию.
   - `/my-assets`: вкладки статусов со счётчиками. Опубликовать новый актив (живое превью, **Save draft** / **Publish asset**), отредактировать, **Withdraw**, **Republish**. Черновик можно удалить, опубликованный актив - нельзя.
   - Открыть один из своих опубликованных активов: блок **Matching buyers** показывает пятёрку лучших покупателей со ссылками на их профили.
   - `/messages`: продолжить диалог (Enter отправляет, Shift+Enter - перенос строки).
3. **Менеджер** - войти как `anna@example.com`.
   - `/admin/users`: вкладки со счётчиками, поиск, меню строки. **Suspend** и **Remove** требуют причину; **Restore** - в один клик. У менеджеров действий нет (их нельзя заблокировать или удалить, в том числе самому себя).
   - **View** в меню строки открывает страницу участника только для чтения: данные аккаунта, причина блокировки или удаления, интересы покупателя или активы продавца. Работает и для удалённых.
   - `/admin/assets`: все статусы, фильтры, **Validate**, **Remove from listings** с причиной.
   - Модерацию лучше пробовать на пользователе, которого вы зарегистрировали сами: **Remove** в интерфейсе отменить нельзя.
4. **Заблокированный пользователь** - войти как `mark.silva@example.com` (покупатель) или `seller.cyprus@example.com` (продавец). На каждой странице баннер с причиной, все изменяющие действия отключены, и сервер отклоняет их, даже если включить кнопку через DevTools. История диалогов видна, поле ввода заменено уведомлением.
5. **Удалённый пользователь** - `seller.gulf@example.com` при входе получает «This account has been removed from the platform.»
6. **Пустой профиль** - `irina.kowal@example.com` не показывается продавцам и видит подсказку заполнить интересы.
7. **Скрытые ресурсы - 404, а не 403** - под покупателем открыть id черновика или удалённого актива (видны в `/my-assets` продавца) или `/admin/users`: ответ одинаковый - «Page not found». Также попробуйте `?page=999` в любом списке.

## Локальный запуск

Требования: Node.js 22+, npm, база PostgreSQL (подойдёт бесплатный проект Supabase; для локальной работы - любой Postgres).

```bash
npm install
cp .env.example .env          # затем заполнить три значения ниже
npm run db:migrate            # применяет миграции (prisma migrate dev)
npm run db:seed               # 16 демо-пользователей, 45 активов, 8 диалогов
npm run dev                   # http://localhost:3000
```

Переменные окружения (`.env.example`):

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение в рантайме. Для Supabase: **transaction pooler** (порт 6543) с `?pgbouncer=true&connection_limit=1`. |
| `DIRECT_URL` | Используется миграциями. Для Supabase: **session pooler** (порт 5432). Не использовать прямой хост `db.<ref>.supabase.co`, он только IPv6. |
| `SESSION_SECRET` | Подписывает токен сессии, минимум 32 символа. `openssl rand -base64 32` |

Скрипты: `dev`, `build` (`prisma generate && prisma migrate deploy && next build`), `start`, `lint`, `typecheck`, `test`, `db:migrate`, `db:seed`, `db:reset` (удаляет всё и заново заполняет - разрушающая операция).

Проверки перед релизом: `npm run typecheck && npm run lint && npm run test && npm run build`.

Деплой: импортировать репозиторий в Vercel, задать три переменные, задеплоить. `vercel.json` закрепляет функции в `fra1`, рядом с регионом Supabase.

## Ключевые технические решения

- **Full-stack на Next.js, без отдельного бэкенда.** Server Components читают данные, Server Actions пишут. Один деплой, меньше связок, и это совпадает с направлением, в котором движется сам N5Deal. Каждое действие валидирует ввод zod-схемой, общей для формы и сервера.
- **PostgreSQL на Supabase с Prisma 6.** Prisma даёт типизированную, удобную для ревью схему и версионированные миграции. Версия 6 закреплена намеренно: без driver-адаптеров и без `prisma.config.ts`, это упрощает настройку пулера. Рантайм идёт через transaction pooler, миграции - через session pooler.
- **Аутентификация: email и пароль, bcrypt, подписанный JWT в httpOnly cookie** (`jose`, HS256, 7 дней, `SameSite=Lax`, `Secure` в продакшене). Токен содержит только id пользователя; **пользователь загружается из базы на каждом запросе**, поэтому блокировка или удаление срабатывают сразу, а роль никогда не берётся с клиента. Ошибка входа одинакова для неизвестного email и неверного пароля, а для неизвестных email сравнивается фиктивный хеш, чтобы время ответа не отличалось. `?next=` принимает только относительные пути того же источника.
- **Правила доступа в одном модуле** (`src/features/access/visibility.ts`): `where`-условия для каждого каталога, проверки для отдельных страниц, правила связи и модерации. Запросы и действия импортируют их оттуда, на страницах нет разрозненных проверок статусов. Всё, что пользователю видеть нельзя, - **404**, чтобы не раскрывать существование ресурса. Скрытие кнопки - только удобство; каждый Server Action заново проверяет сессию, роль, статус пользователя и владение.
- **Записи, которые не должны конфликтовать, условные.** Смена статуса идёт через `updateMany` с проверенным статусом в условии, а модерация пишет смену статуса и запись `ModerationLog` в одной транзакции. Создание диалога берёт advisory lock на пару и перечитывает статус второй стороны внутри транзакции.
- **Мягкое удаление.** Пользователи никогда не удаляются физически: `REMOVED` скрывает их контент и блокирует вход. Опубликованные активы никогда не удаляются физически (на них могут ссылаться диалоги); продавцы снимают их с публикации (`ARCHIVED`), менеджеры удаляют с причиной (`REMOVED`). Удалять можно только черновики.
- **Массивы Postgres для интересов покупателя** (страны, типы лицензий, категории, типы активов). Справочники маленькие и фиксированные, фильтры используют `hasSome`, при росте можно добавить GIN-индекс. Это избавляет от четырёх связующих таблиц без всякой пользы.
- **Состояние фильтров, поиска, сортировки и страницы хранится в URL.** Перезагрузка и кнопка «назад» его сохраняют, ссылками можно делиться. После первой загрузки списки не показывают скелетоны: при изменении старый список остаётся с пониженной прозрачностью и тонкой полосой прогресса, поэтому ничего не прыгает.
- **Подбор - чистая функция** (`features/matching/score.ts`) с тестами. Критерий учитывается, только если покупатель его задал; цена по запросу в сравнении с бюджетом не участвует. «Best match» сортирует в памяти по отфильтрованному набору (для прототипа нормально, см. ниже).
- **Структура по фичам, без DDD и CQRS.** В папке каждой фичи лежат вместе `queries.ts`, `actions.ts`, `schema.ts` и компоненты; страницы остаются тонкими. Осознанный выбор для прототипа такого размера.
- **Дизайн-система.** Tailwind с токенами в `globals.css`, компоненты shadcn/ui перекрашены под вид N5Deal (pill-кнопки, карточки со скруглением 20px, чёрная «пилюля» активного пункта меню). В интерфейсе нет сырых значений enum: подписи берутся из одного справочного модуля, цены и даты - из одного модуля форматирования (даты в UTC, чтобы сервер и браузер выводили одну и ту же строку).

## Модель данных

[ER-диаграмма Mermaid - без изменений, см. английскую версию]

Пояснения к статусам:

- **Пользователь:** `ACTIVE` - обычное состояние. `SUSPENDED` может войти и видит баннер с причиной, но ничего не может менять и отправлять; его профиль и активы скрыты из каталогов, менеджер может его восстановить. `REMOVED` не может войти и скрыт везде; в интерфейсе это необратимо (в реальной системе было бы обратимо и подчинялось бы политике хранения данных).
- **Актив:** `DRAFT` (только владелец и менеджер) → `PUBLISHED` (все, если продавец активен) ⇄ `ARCHIVED` (снят владельцем, может опубликовать снова). `REMOVED` ставит менеджер с причиной; владелец видит причину и не может редактировать или публиковать заново. `validatedAt` - независимый знак доверия («Validated»), а не условие публикации.
- **Диалог** уникален для (покупатель, продавец, актив). Postgres не считает два `NULL` равными, поэтому уникальный индекс не покрывает общие диалоги (`assetId = null`); этот случай проверяется в коде через `findFirst` внутри транзакции под advisory lock.
- Последовательность `Asset.id` в первой миграции перезапускается с 700, чтобы id выглядели как на реальном сайте («Asset ID #751»).
- `ModerationLog` пишется при каждом действии модерации, в той же транзакции, что и изменение. Страницы для его просмотра пока нет (см. ниже).

## Допущения

- **Профиль покупателя «заполнен»**, если задано хотя бы одно из: страны, типы лицензий, категории или бюджет. Одни только типы активов не считаются. Покупатели с пустым профилем продавцам не показываются и видят подсказку заполнить интересы.
- **Кто кому может писать:** покупатель пишет продавцу со страницы актива, продавец пишет покупателю со страницы его профиля. Покупатель покупателю, продавец продавцу, самому себе и всё, что связано с менеджером, отклоняется. Менеджеры в переписке не участвуют.
- **Заблокированным и удалённым участникам** нельзя написать, и сами они писать не могут. В существующих диалогах история сохраняется, поле ввода заменено уведомлением.
- **Диалог - на пару и актив:** если он уже есть, кнопка называется «Open conversation», а не создаёт второй. Общий диалог (без актива) можно начать со стороны продавца.
- **Активы публикуются без предварительной модерации.** «Validated» - отдельный, более поздний знак доверия от менеджера.
- **Опубликованные активы заблокированного продавца остаются в базе опубликованными**, но пропадают из каталогов на время блокировки и возвращаются после восстановления.
- **Менеджер не может заблокировать или удалить ни одного менеджера,** включая себя; это проверяет сервер.
- **Цена по запросу** (`null`) - полноценное значение: так и отображается, сортируется последней и не влияет на совпадение по бюджету.
- **Валюта только EUR,** целые евро.
- **Черновику нужно лишь несколько полей** (headline, категория, тип лицензии, тип актива, статус бизнеса, страна); публикация запускает полную валидацию.
- **Даты показываются в UTC.**

## Обработанные пограничные случаи

- `?page=999`, `?page=abc`, дробные или огромные номера страниц: редирект на последнюю страницу или откат на первую.
- Мусор в любом параметре URL (`?sort=garbage`, неизвестные значения enum, нечисловые цены): откат к значениям по умолчанию, без исключений. Диапазон цены или бюджета, введённый наоборот, меняется местами.
- Нечисловые или чужие id в URL активов, покупателей и диалогов: 404 с той же страницей, что и для несуществующего ресурса.
- Чужая роль на странице (покупатель открывает `/admin/users`, продавец - `/assets`): 404.
- Открытые редиректы через `?next=` (`//evil.com`, `/\t/evil.com`, `/..//evil.com`, обратные слеши, управляющие символы) отклоняются и покрыты тестом.
- Вход: одна ошибка для неизвестного email и неверного пароля; email хранится и сравнивается в нижнем регистре; удалённый аккаунт получает своё сообщение; заблокированный может войти и видит баннер.
- Пользователь, заблокированный или удалённый во время сессии, отрезается на следующем запросе (статус читается из базы каждый раз). То же самое перепроверяется внутри транзакции при отправке сообщения.
- Заблокированный пользователь ничего не может изменить, даже если включить отключённую кнопку: каждый Server Action проверяет статус на сервере.
- Одновременные изменения: снятие, повторная публикация, редактирование, подтверждение и удаление актива выполняются при условии прочитанного статуса; устаревшая запись получает «The record has changed, reload the page and try again».
- Двойная отправка: кнопки отключаются на время действия; отправка сообщения оптимистичная с состоянием «Sending...», а неудачная отправка показывает «Not sent» с Retry (в том числе при потере соединения).
- Одновременное создание одного и того же диалога не порождает дубль (advisory lock плюс `findFirst`, потому что `NULL` не покрывается уникальным индексом).
- Продавец, чей актив удалил менеджер, видит причину и не может его редактировать или опубликовать заново, в том числе прямым вызовом действия.
- Покупатель, очистивший профиль, исчезает из каталога продавцов, а первое сообщение ему отклоняется, если это произошло, пока продавец писал.
- Длинные имена, заголовки и названия компаний обрезаются многоточием с полным текстом в подсказке; раскладка не сдвигается при загрузке списков, смене фильтров и раскрытии тегов «+N».
- У каждого списка есть пустое состояние с действием; каждое разрушающее действие требует подтверждения; каждое действие даёт обратную связь (тост или видимое изменение).
- Неожиданные ошибки рендера показывают страницу ошибки приложения с «Try again» вместо стандартной страницы фреймворка.

## Какие AI-инструменты использовались

Проект я сделал с **Claude Code** (Anthropic) в рамках 24 часов на задание. Claude (чат) использовал, чтобы вместе составить ТЗ и проверять скриншоты интерфейса. Продуктовые и инженерные решения - мои; агент работал в рамках, которые задал я:

- **Сначала ТЗ.** До кода я подготовил ТЗ на реализацию (объём с разбивкой MUST / SHOULD / COULD, правила доступа, модель данных, экраны, дизайн-токены) и список задач с критериями «готово, когда». Источником правды было задание: если ТЗ ему противоречило, я останавливался и разрешал противоречие, прежде чем идти дальше.
- **Задача за задачей.** Claude Code реализовывал по одной задаче через скилы проекта (`/task`, `/phase-check`, `/status`). Я проверял и принимал каждый результат до начала следующей задачи. Проектный `CLAUDE.md` и правила по путям (доступ, данные, UI) держали его в рамках стека, структуры и соглашений; добавлять библиотеки, поля или экраны, не описанные в ТЗ, он не мог.
- **Ревью отдельными агентами.** Сабагенты только на чтение проверяли код по ТЗ: один - правила доступа, второй - UI и дизайн-токены, третий - критерии задач. Они нашли реальные проблемы, например обход open-redirect в `?next=` (`/\t/evil.com`, позже `/..//evil.com`), окна гонок в транзакциях сообщений и проблемы контраста. По каждой находке я решал, исправить её или записать как известное ограничение.
- **Ручное ревью.** Я прошёл каждый экран под каждой ролью в браузере и поймал то, что пропустили автоматические проверки: в превью карточек в профиле и форме актива были живые кнопки «Contact» (пользователь мог написать сам себе), селект актива на странице покупателей читался как ещё один фильтр, шапка дёргалась в конце скролла, над списками было слишком много пустого места. Каждое исправление уходило агенту отдельной задачей.
- **Проверки.** `typecheck`, `lint`, `build` и тесты запускались после каждой задачи; схема менялась только через миграции; разрушающие команды для базы выполнял только я.
- **Также проверено руками:** правила доступа (404, заблокированные и удалённые аккаунты), визуальное соответствие n5deal.com, продакшен-деплой и seed. Решения и отступления от плана фиксировались по ходу работы.

## Что улучшил бы при наличии времени

- **Страница журнала модерации** (`/admin/log`). Данные уже пишутся при каждом действии; страница отложена из-за времени.
- **AI-функции:** поиск на естественном языке («licensed EMI in the EU under 5M»), превращаемый в фильтры, умная валидация описаний активов, подсказки ответов.
- **Полноценная аутентификация:** подтверждение email, сброс пароля, rate limiting и блокировка входа после попыток, отзыв сессий на сервере (сейчас выход только удаляет cookie, и токен живёт 7 дней, хотя удалённый пользователь отрезается сразу). Демо-аккаунты с общим паролем - только для проверки.
- **Модерация до публикации** и обратимое удаление пользователей с политикой хранения данных.
- **Realtime и уведомления:** сообщения в реальном времени, счётчики непрочитанных (поля для отслеживания прочтения уже есть), email-уведомления.
- **Подбор в SQL.** «Best match» сортирует в памяти по отфильтрованному набору; при росте это переезжает в запрос с GIN-индексом на массивах интересов. Следующий шаг - хранимая оценка для каждой пары (покупатель, актив).
- **Мультиязычность** и цены в разных валютах.
- **End-to-end тесты** (Playwright) для основных сценариев: связь, публикация, модерация, заблокированные пользователи.
- **Массовые действия модерации** в таблицах менеджера.
- **Известное ограничение:** layout приложения не перерисовывается при мягкой навигации внутри сегмента, поэтому баннер блокировки или меню могут быть устаревшими до следующей полной загрузки, если менеджер меняет статус во время сессии. Серверные проверки это не затрагивает.
